# Миграция на PostgreSQL + упаковка в Docker

Дата: 2026-11-10
Статус: approved (design), ожидает review перед передачей в writing-plans

## Контекст

Kanban-приложение (Flask + сырой `sqlite3`, монолитный `app.py` ~4700 строк, ~594 вызова
`conn.execute`) сейчас работает на Windows-сервере вручную запущенным процессом
(`python serve.py` / `run_kanban.bat`), без зарегистрированной службы. Хранилище —
файл `kanban.db` (SQLite) + директории `uploads/` (вложения карточек) и
`static/uploads/` (аватары, фоны досок). Пользователи и права доступа к доскам
берутся либо из Google Sheets (`sheets.py`, `gspread`), либо из локальной таблицы
`users` как fallback.

Приложение уже используется в бою с реальными данными компании. Цель этой работы —
подготовить переход на управляемую инфраструктуру: сначала перевести хранение на
PostgreSQL, затем упаковать всё в Docker и перенести на отдельный Linux-сервер.

## Цели

1. Заменить SQLite на PostgreSQL как основное хранилище данных, без потери и без
   искажения существующих боевых данных.
2. Упаковать приложение и БД в `docker-compose` (сервисы `app` + `db`).
3. Перенести эксплуатацию с текущего Windows-сервера (ручной процесс, без службы)
   на отдельный Linux-сервер, доступный только из внутренней сети компании (как
   сейчас), с исходящим доступом в интернет (Google Sheets API, `docker pull`,
   обновления пакетов).
4. Уложить переключение в окно обслуживания 1–2 часа вечером/в выходные, с
   возможностью безопасного отката на старую систему, если что-то пойдёт не так.

## Не цели (explicitly out of scope)

- Внешний доступ по HTTPS/домену — не нужен, остаётся только внутренняя сеть.
- Замена Google Sheets как источника пользователей — не трогаем, механизм остаётся.
- ORM или query-builder (SQLAlchemy и т.п.) — решили не вводить, см. «Рассмотренные
  и отклонённые варианты».
- Нулевой даунтайм / dual-write — не требуется, окно 1–2 часа согласовано.
- Миграция `completed`/`archived`/`active` и т.п. колонок с `INTEGER` (0/1) на
  нативный Postgres `BOOLEAN` — оставляем `INTEGER`, чтобы не трогать код, который
  сравнивает эти поля как truthy-int.

## Рассмотренные и отклонённые варианты (перенос кода на новый диалект SQL)

Рассматривались три варианта переноса ~594 вызовов `conn.execute` на Postgres:

- **Прямой перенос диалекта (выбран).** Меняем драйвер на `psycopg2`, механически
  правим различия диалектов на местах. Предсказуемо, проверяемо при код-ревью, не
  добавляет зависимостей.
- **SQLAlchemy Core как слой абстракции.** Отклонён — не снимает необходимости
  переписывать SQLite-специфичные конструкции (та же работа руками), добавляет
  только лишнюю зависимость и кривую изучения ради мультибазовости, которая
  проекту не нужна (Postgres — конечная точка, не промежуточный вариант).
- **Прослойка совместимости с подменой SQL "на лету"** (патч `execute()`, чтобы сам
  транслировал `?`→`%s` и SQLite-функции в рантайме). Отклонён — хрупкое решение
  для боевых данных компании: текстовая подмена SQL-строк даёт ложные
  срабатывания и неявное поведение, которое тяжело отлаживать.

## Архитектура целевого состояния

```
Linux-сервер (внутренняя сеть компании)
├── docker-compose.yml
│   ├── service: db   → postgres:16, volume pgdata:/var/lib/postgresql/data
│   └── service: app  → Dockerfile (python:3.11-slim), waitress (serve.py)
│       ├── volume ./uploads          → /app/uploads
│       ├── volume ./static/uploads   → /app/static/uploads
│       └── volume ./google_credentials.json → /app/google_credentials.json:ro
└── cron/compose-сервис: pg_dump бэкап БД + копирование uploads (ежедневно)
```

Сеть между `app` и `db` — внутренняя docker-сеть compose, `db` порт наружу не
публикуется. `app` публикует `5001` на хост (без nginx/TLS — доступ только из
внутренней сети, как согласовано).

## Изменения в коде приложения

### Слой подключения к БД (`models.py`)

- `get_db()`: `sqlite3.connect(...)` → `psycopg2.connect(...)`, курсор —
  `psycopg2.extras.RealDictCursor` (чтобы `row['col']` и `dict(row)` продолжали
  работать без изменений в вызывающем коде).
- Параметры подключения — из переменных окружения (`POSTGRES_HOST`,
  `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`),
  читаются через уже используемый `python-dotenv`.
- `PRAGMA foreign_keys = ON` — убирается (Postgres всегда enforce FK).
- `init_db()`: DDL переписывается под Postgres —
  `INTEGER PRIMARY KEY AUTOINCREMENT` → `INTEGER GENERATED ALWAYS AS IDENTITY
  PRIMARY KEY`; `datetime('now','localtime')` в `DEFAULT` → `to_char((now() AT
  TIME ZONE 'UTC') + interval '5 hours', 'YYYY-MM-DD HH24:MI:SS')` (колонка
  остаётся `TEXT`, формат строки идентичен нынешнему — шаблоны/JS, парсящие эти
  строки, не трогаем). Используется фиксированный оффсет `UTC+5` (подтверждено
  пользователем), а не именованная IANA-зона — это осознанный выбор, чтобы не
  зависеть от tzdata на хосте и от возможных правил перехода на летнее время.

### `migrate_db()` (app.py)

Текущий паттерн — `ALTER TABLE ... ADD COLUMN ...` обёрнутый в try/except
(в SQLite нет `IF NOT EXISTS` для колонок). В Postgres это нативно
поддерживается, переписываем каждую миграцию как:
```sql
ALTER TABLE cards ADD COLUMN IF NOT EXISTS ai_summary TEXT;
```
без try/except — миграции становятся проще и явно идемпотентны.

### Точки расхождения диалекта в `app.py` (~594 вызова `conn.execute`)

| Паттерн | Кол-во | Замена |
|---|---|---|
| `?` плейсхолдер | ~594 | `%s` (скриптовая замена regex + ручное построчное ревью диффа перед коммитом) |
| `cur.lastrowid` | 31 | `... RETURNING id` + `cur.fetchone()['id']` |
| `INSERT OR IGNORE` | 17 | `INSERT ... ON CONFLICT (<колонки>) DO NOTHING` — разбирается вручную по месту, конфликтующий constraint для каждого случая свой (например, `board_access`: `ON CONFLICT (user_id, board_id)`) |
| `datetime('now','localtime')` в запросах (не DDL) | 26 | `to_char(now() AT TIME ZONE 'Asia/Almaty', 'YYYY-MM-DD HH24:MI:SS')` |
| `executescript` | 26 (гл. образом DDL в `init_db()`/`migrate_db()`) | `psycopg2` выполняет несколько `;`-разделённых statements без параметров за один `execute()` — подходит для DDL-блоков как есть |

### Фикс абсолютных путей вложений (`attachments.filepath`)

Обнаружено при анализе: `filepath` в таблице `attachments` хранит **полный
абсолютный путь** (`os.path.join(UPLOAD_FOLDER, ...)`), вычисленный на Windows
(`C:\...\uploads\...`). При переносе на Linux эти пути станут невалидными, и
скачивание старых вложений сломается. Это должно быть исправлено как часть
переноса (не отдельная будущая задача), двумя шагами:
1. При ETL-переносе данных — one-off `UPDATE attachments SET filepath = ...`
   на новый Linux-путь (`/app/uploads/<board_id>/<filename>`, соответствующий
   новому `UPLOAD_FOLDER` в контейнере).
2. Код создания новых вложений (`app.py`, роут загрузки вложений) не меняется
   по сути — он и так строит путь через `os.path.join(UPLOAD_FOLDER, ...)`,
   просто `UPLOAD_FOLDER` в контейнере станет `/app/uploads`.

## Перенос данных работающего приложения

### Подготовка (заранее, без риска для прод-системы)

1. Разворачивается Linux-сервер + `docker-compose` с пустым Postgres, применяется
   новая схема (`init_db()`).
2. Генеральная репетиция: копия текущего `kanban.db` + `uploads/` прогоняется
   через ETL на тестовом контуре, результат проверяется по чек-листу ниже. Это
   даёт точную оценку времени и исключает сюрпризы в реальное окно.

### Окно обслуживания (1–2 часа)

1. Остановить Windows-процесс (`serve.py`). `kanban.db` и `uploads/` на Windows
   **не удаляются и не изменяются** — это страховка для отката.
2. Скопировать актуальные `kanban.db`, `uploads/`, `static/uploads/` на
   Linux-сервер (scp/rsync).
3. Запустить одноразовый ETL-скрипт `migrate_to_postgres.py`:
   - читает таблицы из SQLite в порядке зависимостей FK (users → workspaces →
     boards → board_access → columns → cards → остальные таблицы,
     зависящие от cards/boards);
   - вставляет строки в Postgres **с сохранением исходных ID** (на них
     завязаны все внешние ключи);
   - после загрузки каждой таблицы — `SELECT setval('<table>_id_seq', (SELECT
     MAX(id) FROM <table>))`, чтобы новые записи продолжали нумерацию без
     коллизий;
   - выполняет `UPDATE attachments SET filepath = ...` (см. раздел выше).
4. Поднять `docker-compose up -d`, прогнать smoke-тест (чек-лист ниже).
5. Только при успешном прохождении чек-листа — переключить внутренний
   DNS/файрвол на новый сервер.

### Откат

Поскольку Windows-сервер и его `kanban.db`/`uploads/` не изменяются в процессе
переноса (только читаются), откат на любом шаге после остановки Windows-процесса
и до переключения DNS/файрвола — это просто повторный запуск `serve.py` на
Windows. Данные не теряются и не рассинхронизируются, так как пользователи не
начинают писать в новую систему до переключения доступа.

## Docker / docker-compose

```
Dockerfile              # python:3.11-slim, pip install -r requirements.txt, CMD python serve.py
docker-compose.yml      # сервисы: app, db
.env                    # POSTGRES_PASSWORD, SECRET_KEY, GOOGLE_CREDENTIALS_PATH, USERS_SHEET_ID (не в git)
```

- `db`: `postgres:16`, volume `pgdata:/var/lib/postgresql/data`, без публикации
  порта наружу.
- `app`: собирается из `Dockerfile`, `depends_on: db` + healthcheck на
  готовность Postgres перед стартом; volumes — `./uploads:/app/uploads`,
  `./static/uploads:/app/static/uploads`,
  `./google_credentials.json:/app/google_credentials.json:ro`; порт `5001`
  публикуется на хост (внутренняя сеть, без nginx/TLS).
- `DATABASE_URL`/`POSTGRES_*` передаются в `app` через `.env`.

## Бэкапы и мониторинг

- Вместо копирования файла `kanban.db` (текущая `Фаза 5` деплой-роадмапа) —
  ежедневный `pg_dump` (cron на хосте или отдельный лёгкий контейнер),
  ротация 30 последних бэкапов.
- `uploads/` и `static/uploads/` — остаются файлами на диске хоста (volumes),
  бэкапятся как раньше (копирование директории).
- `/health` эндпоинт остаётся, дополняется реальным запросом к Postgres (одна
  строка), чтобы отличать обрыв соединения с БД от просто живого процесса Flask.

## Тестирование и критерии приёмки

**До переноса (staging/репетиция):**
- Построчная сверка количества строк по каждой таблице: SQLite == Postgres
  после ETL.
- Контрольная сумма по паре таблиц (например, hash от конкатенации всех
  `cards.title`) — SQLite vs Postgres.
- Проверка FK-целостности: 0 строк в Postgres с внешним ключом, ссылающимся на
  несуществующий id.

**Чек-лист smoke-теста (и на репетиции, и в реальное окно, до переключения
доступа):**
1. Логин (Google Sheets, если настроен, и fallback через локальных users).
2. Открыть доску → колонки/карточки на месте; drag&drop карточки между
   колонками работает (проверяет перенесённый `board_access`/`card_watchers` и
   reorder-логику).
3. Открыть карточку с вложением → скачать вложение (проверяет фикс
   `filepath`).
4. Добавить комментарий и пункт чек-листа (проверяет `lastrowid` →
   `RETURNING id`).
5. Создать новую карточку и новую доску (проверяет `IDENTITY`/`setval` после
   переноса).
6. Экспорт CSV доски и workspace.
7. `GET /health` → 200, с реальным обращением к Postgres.

**Критерий приёмки:** все 7 пунктов проходят на репетиции (копия данных), и
повторно — в реальное окно на боевых данных, до переключения внутреннего
доступа сотрудников на новый сервер.

## Риски

- 594 места с `conn.execute` — большой объём ручного ревью диффа после
  скриптовой замены плейсхолдеров. Снижается тем, что замена `?`→`%s`
  механическая и легко вычитывается построчно, а 17 `INSERT OR IGNORE` и 31
  `lastrowid` разбираются вручную (не предполагают автозамены).
- Таймзона: Linux-сервер по умолчанию может быть в UTC, в отличие от текущего
  Windows-сервера. Подтверждено пользователем — текущий сервер работает в
  `UTC+5`; это зафиксировано как явный оффсет в SQL-выражениях формирования
  временных строк (см. выше), не полагаясь на TZ хостовой ОС Linux-сервера.
- Путь вложений (`attachments.filepath`) — найденная при анализе проблема,
  учтена в плане миграции данных (см. выше), не отдельная будущая задача.
